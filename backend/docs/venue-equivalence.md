# Explicit physical-ground equivalence

Local implementation only. No link is created by the migration. A separately reviewed SQL write is required to activate any equivalence; there is no new administrative endpoint, fuzzy matching or automatic cleanup.

`venues.canonical_venue_id` is a direct FK to a physical root. NULL means this venue is a root. `equivalence_source` records the reviewed evidence for a non-NULL link. IDs, existing venue rows and all historical references remain unchanged. The database rejects missing roots, missing provenance, self-links, chains/cycles, changing an approved destination and turning a root with incoming links into another alias. Graph edits use one transaction advisory lock. Ordinary application roles must not be allowed to disable these checks or activate unreviewed links.

`ingestion.venue_identity.CanonicalVenues` is the shared pure resolution contract; `backend/venue_resolution.py` provides a session-scoped bulk loader, API errors, equivalent-ID groups and non-mutating response projections. The loader reads at most 10,001 links and fails closed above 10,000. No global cache, network lookup or recursive traversal. Valid FK targets are enforced by the database; requested missing venues return 404. Session-local caching assumes equivalence edits occur only through the separately reviewed maintenance procedure, not during an application request.

All new manual/fixture-linked attendance resolves to the root. Existing records are returned/projected under the physical identity but never have their stored venue ID rewritten. Existing same-day manual reconciliation and one-owner/fixture rules remain; repeat matchdays stay separate. Writes serialise by physical ground via a transaction advisory lock, including empty-row cases. This coarse lock favors correctness for beta; monitor contention before a broader release.

Owned Footprint groups raw visits on root metadata, preserving every visit ID/date/fixture and undated history. League drift validation compares reviewed Team/ClubVenue venue IDs through the explicit resolver; unrelated venue, role or date changes still fail closed. An ingestion update from a reviewed alias to its root is therefore not mistaken for a different home ground. Shared grounds can credit multiple verified clubs but have one map pin/physical-ground count. An explicit equivalence does not itself verify unknown league membership or override Coverage incomplete: Bromley's League One catalogue refresh remains a separately reviewed activation dependency.

Personal review writes look across the entire physical group. A single legacy review stays editable under either URL without changing its stored venue ID. Multiple reviews for one owner/physical ground fail closed (409), including owned summary/review reads; no row is overwritten or silently selected. Public aggregates exclude that ambiguous owner/physical-ground pair, rather than merging or double-weighting scores. Resolving such a conflict requires a separate approved process, not this migration.

Photo payloads and venue/discover grouping resolve physical IDs. Public eligibility, cursor order, owner/attendance identity, moderation, consent, storage keys, attribution and signed delivery remain unchanged. Search preserves matches on legacy aliases but returns canonical ground metadata once. Saved legacy venue links remain readable and return the canonical ID; no new frontend navigation or HTTP redirect system is introduced.

The forward migration also replaces the existing photo guard with the same ownership/context/transition/quota checks and one changed comparison: the fixture venue and attendance/photo venue must resolve to the same physical root. The photo still has to match its owned attendance's exact stored venue and fixture IDs. This permits a new canonical visit for an unchanged alias fixture without weakening ownership or rewriting photo history. The application reservation check uses the same resolution contract.

Ingestion uses the same explicit graph after provider resolution and manual/direct-name decisions. Provider identity and authority order remain unchanged; no fixture ingestion is run by this feature. Legacy provider refs can remain attached to the source row because their resolved destination is canonical. No provider-ID/canonical-ID numeric equality is assumed.

## Reversal and code recovery

The rollback SQL refuses to proceed if ANY active equivalence exists, or if any active photo has a raw fixture/venue mismatch that would fail the restored original photo guard. An eligible empty-link reversal takes an exclusive venue-table lock, restores the original photo guard and drops the new equivalence trigger/function/columns/index/FK; it does not delete or reassign venue/attendance/review/photo records. Rehearse forward twice, empty rollback/reapply and active rollback refusal on local PostgreSQL.

For active links, do not just drop the columns or roll back to an unaware application. Stop writes, export exact links/evidence and current references, verify compatible recovery code and assess records created after activation. Removing a link can split new canonical visits from old alias visits even though no row was rewritten. Any unactivation must be separately reviewed. The guard intentionally rejects ordinary reassignment/unactivation; an approved maintenance transaction would need an exclusive lock and controlled trigger handling, with exact preconditions, link export and read-back verification. There is no safe universal automatic reversal and no data reversal is attempted here.
